## 第 8 章 单次生成与调参

### 8.1 四象限选型表

| | Ref2VA（图+音→视频） | FL2VA（文+音→视频） |
|---|---|---|
| **NF4**（生产默认） | `batch_ref2va_nf4.py`（批量主力） | `h3_m4_fl2va.py` |
| **Pruned**（快速试参） | `batch-full/h3_pruned_ref2va_batch_resume.py` | `batch-full/h3_pruned_fl2va_batch_resume.py` |

- 多参考图规模化 → `scripts/multi-image-report/` 四件套（每图独立 seed 组）；
- 断点续跑版 vs 旧版：一律用 `batch-full/`（模型只加载一次 + seed 日志）。

### 8.2 关键参数语义

| 参数 | 语义 | 生产值 |
|---|---|---|
| 质量档 | preview（快）/ full（正式） | 夜批 full |
| `SEED_LIST` | 模块级种子表，**必须单行、大小写敏感** | `[42]`（演进后）/ `[42, 10]`（筛选期） |
| `--batch N` | 批次号 → output_batch{N}/ 与 manifest 绑定 | 日期序号递增 |
| 重跑语义 | SUCCESS 跳过；FAILED/SKIPPED **重跑**；半成品 mp4 已被清理 | 断点续跑依据 |

### 8.3 确定性生成（演进策略的公理）

同图+同 seed → **逐位相同产物**。证据：batch1001/1004/1005 跨两天 conf 逐位一致
（1.6276/1.6082），md5 同值。推论：**同图重跑同 seed = 零信息空转**（第 15 章策略基石）。

### 8.4 生成期「正常表象」清单（勿误判）

| 表象 | 判定 |
|---|---|
| 0% CPU + RSS 冻结 ~11GB + 无产物文件 | MPS 扩散中，正常；看 raw 日志进度条 |
| `logs/nightly_*_b*.md.raw` 进度条 260s/it | 正常；>1000s/it 才是争用 |
| bitsandbytes/torch dynamo 重编译 warning | 良性 |
| 首步前 ~3min 无任何日志 | 模型加载，正常 |
| 收到 SIGTERM 后 mp4 消失 | 优雅终止清理半成品，正常（manifest 有 FAILED 留痕） |

### 8.5 优雅终止与手动停止

```bash
# 正规停止姿势（任何来源的 SIGTERM 都会优雅收敛）
pgrep -f batch_ref2va_nf4        # 拿 PID
kill -TERM <pid>                  # → FAILED 留痕 + SKIPPED 补记 + ended_at 写入，exit 143
# Activity Monitor 退出（也发 SIGTERM）等价；绝不 kill -9（防线二才兜得住）
```

**验收**：能给定需求（快试参/正式产/多图）选出脚本与档位；能安全停止一次生成并复述 manifest 变化。

## 第 9 章 夜间批量流水线全解（nightly_run.sh v1.4.0）

### 9.1 执行序总图

```
cron(22:00) ──> nightly_run.sh
  ├─ 0. export PATH（v1.3.0，防 ffmpeg 失明）
  ├─ 1. ⑥ 并发守卫：pgrep pipeline_auto|batch_ref2va → 存活即拒绝退出（H3_FORCE 不豁免）
  ├─ 2. 电源门禁：非 AC Power 拒启
  ├─ 3. caffeinate re-exec（防休眠，事故②）
  ├─ 4. 窗口守卫：非 22:00-08:00 拒启
  ├─ 5. 批次决策：H3_BATCH 指定 / --auto 自动编号
  ├─ 6. 报告初始化 logs/nightly_YYYYMMDD_b{batch|auto}.md（v1.4.0 按批次命名，防覆盖）
  └─ 7. 执行 pipeline_auto --auto --batch N → ①生成 ②评分 ③归档 ③.5收敛 ④⑤面板刷新
       └─ 完成后 raw 合并定稿 → cron 日志收尾
```

### 9.2 六 stage 与失败表现对照表

| Stage | 动作 | 失败表现 | 处置 |
|---|---|---|---|
| ① 生成 | batch_ref2va（subprocess） | exit 143=被停/1=崩；manifest 是真相 | 晨检按 12 章判 |
| ② 评分 | score_lipsync 全部 seed | **exit 1 + stderr ⚠**（v1.2.0）；heuristic 降级=ffmpeg 缺 | 补评：`--force` |
| ③ 归档 | archive_to_nas 双速制 | NAS 断链 → .nas_pending（不 fail 主链） | 恢复后自动补 |
| ③.5 收敛 | reconcile_batches --apply | 0 僵尸=正常 | 见第 16 章 |
| ④ 分析 | analyze_report（auto 下推荐 []） | — | 人工打分后重跑 |
| ⑤ 面板 | export_dashboard_data + seed_list 更新 | update_seed_list 失败 exit 1 会显式标红 | 第 15 章 |

### 9.3 并发守卫细则（v1.4.0）

```bash
# 拒绝条件：pgrep -f "pipeline_auto.py" 或 "batch_ref2va" 有活体
# 关键语义：H3_FORCE 只豁免窗口门禁，绝不豁免并发守卫（双生成无赢家）
# 22:00 cron 撞上白天手动批 → cron_nightly.log 留一行拒绝痕，无害
```

⚠️ 守卫测试规约：**必须隔离验证（pgrep 干跑/双分支），禁止整体执行编排脚本**；
诱饵进程必须保活（`<<<` 瞬退诱饵曾致测试走火真实拉起 batch1005——事故④附案）。

### 9.4 报告文件学

- 命名 `logs/nightly_YYYYMMDD_b{batch|auto}.md`：同日多批不互相覆盖（09-29 事故④根治）；
- `.raw` 为过程日志，定稿时合并进 `.md` 后删除——**raw 消失 = 流水线跑完或死透**；
- 头注释维护四起事故加固实录（①PATH ②休眠 ③ffmpeg ④GPU 争用），改脚本必读。

### 9.5 cron 安装与查看

```bash
crontab -l | grep nightly    # 0 22 * * * cd .../YYC3-MiniMax-H3 && bash scripts/pipeline-tools/nightly_run.sh >> logs/cron_nightly.log 2>&1
crontab -l | grep reconcile  # 10 8 * * * ... reconcile_batches.py --apply（08:10 兜底收敛）
crontab -l | grep runner     # 10 22 * * * ... video_task_runner.py --loop（任务队列消费）
```

**验收**：能背六 stage 顺序；能解释守卫为何不豁免 FORCE；能说出 raw 文件消失的两种含义。

## 第 10 章 一键流水线 pipeline_auto

### 10.1 五段拆解

| 段 | 脚本 | 输入→输出 | 失败传播 |
|---|---|---|---|
| ① 生成 | batch_ref2va_nf4 | ref_images×SEED_LIST → output_batch{N}/manifest.json | exit 码透传（143/1） |
| ② 评分 | score_lipsync | manifest → lipsync 字段回填 | None→exit 1（告警） |
| ③ 归档 | archive_to_nas.sh | output_batch{N} → NAS | 断链不阻塞（自愈队列） |
| ③.5 收敛 | reconcile_batches | manifest → reconciled 块 | — |
| ④⑤ 分析+面板 | analyze / update_seed_list / export | → analysis_result_batch{N}.md + batches.json | 写回失败 exit 1 标红 |

### 10.2 三模式

```bash
python scripts/pipeline-tools/pipeline_auto.py --batch 1002            # 指定批（续跑）
python scripts/pipeline-tools/pipeline_auto.py --auto --batch 1006     # 夜批自动（cron 用）
python scripts/pipeline-tools/pipeline_auto.py --dry-run               # 预演不落盘
```

- `--auto`：③ 精评跳过人工 → 推荐清单 `[]` → 写回层空守卫跳过（设计内，第 15 章）；
- `AUTO_AFTER_GENERATE=False`（默认）：生成后暂停等人工打分——交互式演进的正确姿势。

### 10.3 白天手动续跑 SOP（最常用命令）

```bash
# 前置四查（第2章 2.1）→ 然后一条命令：
H3_FORCE=1 H3_BATCH=1002 bash scripts/pipeline-tools/nightly_run.sh
# 或直接 pipeline_auto（无报告/归档编排时）
# 注意：H3_FORCE 豁免窗口但不豁免守卫——GPU 有活体照样拒绝
```

**验收**：不看文档写出「续跑 batch1002」完整命令含前置检查；说出 --auto 下推荐清单为何是 []。

## 第 11 章 网关任务队列与 Mac runner（第五能力）

### 11.1 任务生命周期（网关侧）

```
POST /v1/video/tasks ──> queued（Redis 7d TTL + NAS 持久双写）
  → runner 领取（原子 claim）→ running（心跳续租）
    → 回报 succeeded（archive_path）/ failed
  租约过期 → 自动回收 → attempts<2 重排队（=anew 语义，无需人工重试）
```

### 11.2 网关 API 契约（runner 消费的五端点）

| 端点 | 方法 | 用途 |
|---|---|---|
| `/v1/admin/video/tasks/claim` | POST | 原子领取（admin 鉴权） |
| `/v1/admin/video/tasks/{id}/heartbeat` | POST | 心跳续租（防租约回收） |
| `/v1/admin/video/tasks/{id}/result` | POST | 回报成功（**归档由网关侧直写 NAS 卷**） |
| `/v1/admin/video/tasks/{id}/failure` | POST | 回报失败（attempts+1，可重排队） |
| `/v1/video/tasks/*`（列表/详情/result） | GET | 面板侧只读消费（X-API-Key） |

⚠️ 架构要点：**runner 不接触 NAS/ssh**——产物回报后由网关完成归档。Mac 侧 NAS 依赖
只剩夜间批量的 archive_to_nas.sh；两条归档路径互不相干，排障时勿混淆。

### 11.3 runner 循环与双层互斥

```
22:10 cron 启动 --loop → 窗口检查（07:30 截止）→ batch_busy()?  ──是──> 等 5min 重查
                                    │否
                                    ▼
                        领任务（GET claim）→ 任务 id 白名单校验（防投毒）
                        → importlib 隔离调生成 → 回报 → 归档
```

- **互斥铁律**：runner 的 `batch_busy()` 检测到批量生成即强制等待——
  注意这与 nightly ⑥ 守卫是**两层独立防线**（runner 层已有，nightly 层 09-29 后补齐）；
- 双地址：领取/回报走 Tailscale（admin-gateway），面板创建任务上传走 LAN（90s 499 坑）。

### 11.4 零 GPU e2e 演练（验收/调试神器）

```bash
H3_FORCE=1 /opt/miniconda3/envs/h3-m4/bin/python \
  scripts/pipeline-tools/video_task_runner.py --once --dry-run
# 领真任务 → 2 秒样片 → 回报归档 → 面板 succeeded，全程 ~3 秒
```

**验收**：完成一次 dry-run e2e 并在面板看到任务 succeeded；能说出互斥的两层分别防什么。

## 第 12 章 晨检 SOP

### 12.1 五查清单（3 分钟版）

```bash
cd /Users/yanyu/YYC-Cube/YYC3-MiniMax-H3
# ① 报告五 stage
tail -40 logs/nightly_$(date +%Y%m%d)_b*.md
# ② manifest 终态
python -c "import json;m=json.load(open('output_batch<昨夜N>/manifest.json'));print(m['ended_at'],[r['status'] for r in m['records']])"
# ③ 评分后端（syncnet 而非 heuristic；score_norm 非 None）
grep -E "conf|backend" logs/nightly_*.md | tail -4
# ④ NAS 实核（第6章 6.3 三查）
# ⑤ 面板状态
python -c "import json;d=json.load(open('dashboard/data/batches.json'));[print(b['id'],b['status']) for b in d['batches'][-3:]]"
```

### 12.2 判定表

| 结果 | 判定 | 动作 |
|---|---|---|
| ①-⑤ 全绿，双 SUCCESS | ✅ 收工 | git 提交 batches.json（待指令）；日志一行 |
| ①-⑤ 绿但 heuristic 降级 | ⚠ 环境漂移 | ffmpeg PATH 检查（4.3 坑1）→ `score_lipsync --force` 补评 |
| 单 seed FAILED / SKIPPED | partial | 白天空闲即续跑（10.3 命令）；或等夜窗自动补 |
| ended_at=null（罕见） | 僵尸 | `reconcile_batches.py --apply`（防线二 normally 已在 08:10 自动做） |
| 批次号没出现 | cron 没跑/被拒 | `tail logs/cron_nightly.log` 看守卫拒绝痕（无害）或窗口/电源门禁 |

### 12.3 深查版（10 分钟，异常时）

按序：报告 `.raw` 是否残留（=死透）→ 系统日志 `last reboot`（是否重启）→
`pgrep` 残留进程 → NAS 侧 `.nas_pending` → 第 22 章速查表对号入座。

**验收**：用 batch1004（全绿）、batch1002（partial→续跑）、batch1000（僵尸）三个历史案例
各做一次纸面晨检，判定与实际处置一致。
