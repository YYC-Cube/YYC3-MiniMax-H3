## 第 4 章 本机生产环境（Mac M4 Max 128GB）

### 4.1 环境清单

|---|---|---|

### 4.2 性能基线（判异常的标尺）

| 指标 | 基线 | 说明 |
|---|---|---|
| 单 seed 耗时 | **3.6-4.2h**（full 档 124 帧） | batch1004 实测 3.62h 最快；>5h 必有争用 |
| 单步扩散 | ~260s/it × 50 步 | >1000s/it = MPS 争用签名 |
| RSS | 模型加载后 ~11GB，扩散期「冻结」正常 | PerformanceTimer 是**进程单调水印**，非 per-seed 真值 |
| 首步前 | 模型加载 ~3min，0% CPU/RSS 爬升 | MPS shader 编译，静默属正常 |
| seed 间 | `torch.mps.empty_cache()` 已内置 | 防 ~15GB 串行缓存累积（batch1000 教训） |

### 4.3 PATH 三坑（血泪史，必读）

```bash
# 坑1：cron 默认 PATH=/usr/bin:/bin，无 homebrew → ffmpeg 找不到 → 评分静默 None
#   根治：nightly_run.sh v1.3.0 顶部显式 export PATH（置于 caffeinate re-exec 之前）
export PATH="/opt/homebrew/bin:/usr/local/bin:$PATH"

# 坑2：本机 rm 是 __safe_rm_realpath 包装函数，依赖 dirname；受限 PATH 下必崩
#   报错形态："command not found: found"（截断误导）
#   规约：受限 PATH 测试一律 /bin/rm 绝对路径

# 坑3：受限环境复现验证（诊断评分问题首选）
env -i PATH=/usr/bin:/bin /opt/miniconda3/envs/h3-m4/bin/python -c "import shutil; print(shutil.which('ffmpeg'))"
# None=复现 cron 环境；修复后应输出 /opt/homebrew/bin/ffmpeg
```

### 4.4 新机重建 checklist

1. 装 homebrew + ffmpeg → 2. conda 创建 h3-m4（requirements 按 vendor 文档）→
2. SyncNet 权重就位 → 3. 跑第 2 章冒烟 → 4. 三项基线核对（4.2 表）→ 5. cron 重装（见 9.7）。

**验收**：4.1 全表通过 + 能复述 4.3 三坑；给一个「评分 None」案例能 2 分钟定位 PATH。

## 第 5 章 网络拓扑：LAN 与 Tailscale 双平面

### 5.1 双平面对照

| 平面 | 地址 | 适用 | 限制 |
|---|---|---|---|
| LAN | `192.168.3.45` | 同网段大文件上传（防公网 90s 499） | **跨网即断** |
| Tailscale | `100.65.172.88`（yyc3-45-1） | 跨网访问网关/SSH；runner 与面板默认 | relay 有延迟，小文件/控制面首选 |

### 5.2 网关地址策略（三处落点）

| 组件 | 地址 | 理由 |
|---|---|---|
| runner `--admin-gateway` | `http://100.65.172.88:8000` | 跨网领取/回报（默认值已固化） |
| console `GATEWAY_URL` | 同上 | 面板任务代理跨网可用 |
| 任务创建上传参考图 | LAN 直连 | 公网网关 90s 超时 499 实证坑（大 body） |

### 5.3 判活 SOP（铁律：先 TS 后 LAN 再下结论）

```bash
# ① Tailscale 面先探（最权威）
ssh -o ConnectTimeout=8 yyc3-45 "uptime"                 # ssh 别名即 TS IP
curl -s -m 5 http://100.65.172.88:8000/health            # 网关
# ② 都通但 LAN 不通 → 只是 LAN 断，生产不受影响（归档走 ssh 别名）
ping -c 2 192.168.3.45
```

09-30「NAS 宕机 P0」实为 LAN 断链假象——TS 面全通、归档照常成功。**结论：别名优先，
硬编码 IP 只允许出现在「策略性选择」（5.2 表）里。**

### 5.4 坑位

- `192.168.3.45:8000` 写进代码默认值 = 埋雷（runner 曾因此整夜空转领不到任务）；
- console 本地调试网关不通时，先查 `apps/console/src/lib/gateway.ts` 默认值与 env 覆盖。

**验收**：能徒手写出 5.3 判活命令组；能解释为什么归档不怕 LAN 断。

### 6.2 双速制归档（archive_to_nas.sh）

```
快车道（实时）：manifest.json + report + analysis_result_batch{N}.md
                 → 成功才算批次闭环的关键件
慢车道（后台）：mp4 媒体 rsync 断点续传 → 大文件不阻塞主链
失败路径    ：NAS 不可达 → 写 .nas_pending 自愈队列 → 下轮补推
```

### 6.3 归档核验 SOP（报告 ✅ 不免检）

```bash
ssh yyc3-45 "du -sh /Volume1/yyc3_hd/video_batch1005 && \
             ls /Volume1/yyc3_hd/video_batch1005/person_a/*.mp4 | wc -l && \
             ls /Volume1/yyc3_hd/video_batch1005/analysis_result_batch1005.md"
```

三看：容量合理（46M/批级）、mp4 数=成功 seed 数、分析文件在（注意是**带批次号后缀**的新名）。

### 6.4 坑位

- `analysis_result.md` 是废弃旧名——pipeline_auto 写的是 `analysis_result_batch{N}.md`（v1.2.0 起全链统一）；
- 归档窗口期恰逢断链（05:30 事故）：报告 ✅ 与断链时间矛盾时，以 **NAS 实核**为准；
- rsync 断点续传依赖目标端时间戳——勿在 NAS 侧手改归档文件。

**验收**：任取一批次 30 秒内给出 NAS 三查结果。
